# PostgreSQL Authority Migration Design

> **Status:** CURRENT_SPECIFICATION
**Date:** 2026-08-05
**Scope:** Make PostgreSQL the default runtime persistence backend while retaining SQLite as an explicit compatibility and replay backend
**Authority ceiling:** Local PostgreSQL persistence and migration engineering evidence only

## 1. Objective

Move the repository's SQLite-backed runtime and domain persistence to a local PostgreSQL 16 database without weakening idempotency, append-only evidence, optimistic concurrency, replay, or authority boundaries.

The target local resources are:

- login role: `market_regime_alpha`;
- database: `market_regime_alpha`;
- application schema: `market_regime_alpha`;
- bootstrap administrator: the user-supplied local `novel_forge` account.

PostgreSQL becomes the default backend for ordinary runtime and command-line operation only after schema, repository parity, migration integrity, and cutover smoke checks pass. SQLite remains available only through an explicit compatibility selection.

## 2. Current facts and assumptions

Current executable evidence shows:

- approximately twenty SQLite-specific implementation modules;
- SQLite migrations numbered 001 through 015 across domain packages;
- an inline, unversioned SQLite schema for the Daily Runtime Journal;
- SQLite-specific `BEGIN IMMEDIATE`, `PRAGMA`, `INSERT OR IGNORE`, trigger `RAISE`, schema introspection, and autoincrement behavior;
- immutable file Artifacts that remain outside database authority;
- DuckDB and Parquet research storage that is not SQLite and is outside this migration;
- no business `.sqlite`, `.sqlite3`, or `.db` file currently discoverable in the repository, `artifacts/`, or `data/` paths;
- a reachable local PostgreSQL 16.14 instance at the user-supplied host and port;
- neither the `market_regime_alpha` PostgreSQL role nor database existed at design time.

The initial cutover therefore expects a schema-only `0 -> 0` data migration unless the operator supplies one or more SQLite source paths before execution. The migration tooling must remain capable of importing those sources later.

## 3. Non-goals

This work does not:

- migrate DuckDB, Parquet, CSV, immutable Artifact, or source archive contents into PostgreSQL;
- introduce dual-write behavior;
- delete or mutate a source SQLite file;
- introduce unattended trading, broker authority, formal Provider qualification, formal OOS Alpha, authenticated operators, or production qualification;
- claim distributed scheduling, multi-region availability, or cross-database atomicity;
- convert the Legacy FastAPI application into the canonical operator workbench;
- change Constitution documents or domain semantics.

## 4. Chosen approach

The chosen approach is a dual-adapter architecture with a PostgreSQL default:

```text
CLI / Application Composition
             |
      DatabaseSettings
             |
      Repository Protocols
        /            \
PostgreSQL default   SQLite explicit compatibility
        |
market_regime_alpha schema
```

Domain services continue to depend on their existing Repository Protocols. PostgreSQL adapters implement those protocols without changing Candidate, Signal, Forecast, Opportunity, Thesis, Portfolio, Risk, Execution, Position, Holding, Exit, or evidence semantics.

SQLite is preserved to support compatibility tests, historical replay, and controlled rollback before PostgreSQL receives new authority writes. It is not an automatic runtime fallback.

## 5. Credentials and configuration

The bootstrap procedure uses the supplied `novel_forge` administrator only to create and grant the repository resources. Administrator credentials must not be written to the repository, migration reports, logs, shell history generated by repository scripts, or application configuration.

The bootstrap procedure will:

1. create a non-superuser login role named `market_regime_alpha` with a generated local password;
2. create the `market_regime_alpha` database owned by that role;
3. create the `market_regime_alpha` schema;
4. set the role/database search path to that schema and `pg_catalog`;
5. remove unnecessary create privileges from `public` where safe for the dedicated database;
6. verify that the application role has no superuser, replication, or role-creation capabilities.

The generated application DSN is stored only in the Git-ignored repository `.env` as:

```text
MARKET_REGIME_ALPHA_DATABASE_URL=postgresql://...
```

A central `DatabaseSettings` value object loads an explicit `--database-url` or this environment variable. DSN rendering and exception translation must redact the password. The user-supplied administrator DSN is never an application fallback.

PostgreSQL is the CLI default. Missing PostgreSQL configuration fails closed with a typed configuration error. An explicit backend selection and SQLite path are required to use SQLite. Supplying incompatible PostgreSQL and SQLite arguments is rejected.

## 6. PostgreSQL schema governance

PostgreSQL migrations live in a central PostgreSQL persistence package rather than modifying the SQLite SQL files in place. SQLite migrations remain immutable compatibility inputs.

A PostgreSQL migration registry records:

- monotonically ordered version;
- stable migration name;
- SHA-256 SQL checksum;
- UTC application time.

Migration execution takes a database-scoped PostgreSQL advisory lock. Each unapplied version executes transactionally. A version/name/checksum mismatch fails closed. Re-running an unchanged migration set is idempotent.

The PostgreSQL schema ports all currently implemented responsibilities:

- Model Registry and Experiment Governance;
- Opportunity and Thesis decisions;
- Portfolio and Risk decisions, complete-account assessments, and risk routes;
- manual execution, fills, Position books, traceability, and reducing-risk manual intent;
- Thesis health and composite operational evidence;
- Daily Runtime Journal;
- Canonical Lifecycle Runtime Journal;
- Feature Materialization Runtime Journal;
- Controlled Decision-Time Operation Journal;
- Longitudinal Operational Index.

The inline Daily Runtime Journal schema receives an explicit PostgreSQL migration version. Migration numbering and documentation must make its placement unambiguous without rewriting the meaning of historical SQLite version markers.

## 7. Type and constraint mapping

PostgreSQL uses:

- `text` for canonical identifiers, enum-like status values, hashes, and canonical JSON bytes;
- `timestamptz` for semantic instants and migration timestamps;
- `date` for decision and trading dates;
- `bigint generated by default as identity` for database-generated sequence identifiers;
- integer or bigint version and claim tokens with positive/non-negative checks;
- explicit primary, unique, foreign-key, and query indexes.

Canonical JSON remains stored as text so PostgreSQL normalization cannot change bytes that participate in existing hashes. JSON validity is enforced using PostgreSQL 16 JSON predicates or equivalent immutable checks without converting the stored authority bytes to `jsonb`.

SQLite append-only and identity-immutability triggers become PostgreSQL trigger functions. Ordinary repository operations cannot update or delete append-only rows. Terminal-state transitions, command-hash conflicts, authority route conflicts, and immutable identity fields retain their current fail-closed behavior.

SQLite `INSERT OR IGNORE` becomes an explicit `INSERT ... ON CONFLICT` with the exact conflict target. It must never hide an unrelated integrity failure. SQLite `BEGIN IMMEDIATE` concurrency intent is translated using unique constraints, conditional version updates, `SELECT ... FOR UPDATE` where an existing row must be fenced, and PostgreSQL transaction isolation appropriate to each protocol.

## 8. Repository adapters and composition

PostgreSQL adapters are organized by bounded context and implement existing protocols. Shared persistence code is limited to:

- settings and backend selection;
- connection and transaction management;
- PostgreSQL migration execution;
- row shape helpers and typed database exception translation;
- test/bootstrap utilities.

Domain-specific SQL, restoration, replay validation, and conflict mapping remain inside each bounded context. A generic repository or active-record abstraction is out of scope.

Composition roots and CLI entry points select adapters through settings rather than importing SQLite implementations directly. Scripts that currently require `--database <path>` gain the PostgreSQL configuration path and retain SQLite only behind explicit compatibility arguments.

Read-only replay must bind to an existing authority source. PostgreSQL replay reads a transactionally consistent snapshot and does not mutate domain authority. File Artifact publication continues to use its current immutable and crash-safe mechanisms.

## 9. SQLite-to-PostgreSQL migration

The migration command accepts a versioned manifest containing one or more named SQLite sources. Each source entry records:

- absolute source path;
- expected source schema identity;
- expected source file digest when known;
- bounded-context/table ownership;
- quiescence requirement.

The import flow is:

```text
stop SQLite writers
-> open each SQLite source read-only
-> begin stable read snapshots
-> hash source files and schemas
-> require empty PostgreSQL business tables
-> copy rows in foreign-key dependency order
-> repair PostgreSQL identity sequences
-> compare counts, primary-key ranges, and canonical table digests
-> validate foreign keys and domain Readers
-> commit one PostgreSQL import transaction
-> publish an immutable migration report
```

The importer preserves identifier strings, canonical JSON text, timestamps, hashes, versions, sequence identifiers, and event ordering. It does not invent missing records or coerce invalid source values.

All PostgreSQL business tables must be empty for the initial importer. Automatic merge into an already authoritative PostgreSQL database is out of scope. A source schema mismatch, changed source file, unsupported table, target collision, sequence mismatch, row-count mismatch, digest mismatch, foreign-key violation, or Reader reconstruction failure rolls back the complete PostgreSQL import transaction.

The migration report records source identities and digests, schema migration checksums, per-table counts and digests, sequence repairs, validation commands, final result, database server version, and code commit. It excludes credentials and DSNs.

## 10. Cutover

PostgreSQL does not become authority merely because its schema exists. Cutover requires:

1. all PostgreSQL migrations applied and verified;
2. repository contract parity passing;
3. PostgreSQL integration and concurrency tests passing;
4. migration dry-run passing;
5. SQLite writers stopped;
6. a PostgreSQL backup captured;
7. the import transaction and evidence report passing;
8. `.env` selecting the application PostgreSQL DSN;
9. canonical lifecycle and controlled-operation smoke reads/writes passing;
10. final-HEAD validation evidence recorded.

There is no dual-write interval. After cutover, PostgreSQL is the sole runtime database authority and retained SQLite sources are read-only historical inputs.

## 11. Failure handling and rollback

Bootstrap is idempotent only for resources with the expected owner and attributes. A conflicting role or database fails closed rather than changing an unknown resource.

Schema migration failure rolls back the current version and leaves earlier verified versions intact. Checksum drift blocks application startup until reconciled by an explicit forward migration.

Data import is all-or-nothing inside PostgreSQL. Source SQLite files are never deleted or rewritten.

Before PostgreSQL receives a new authority write, rollback may explicitly reselect SQLite only when source and target migration digests still prove equality. After PostgreSQL receives new authority data, returning to a stale SQLite database is prohibited. Recovery must restore PostgreSQL from backup or forward-repair PostgreSQL and the application.

## 12. Verification strategy

Tests are developed contract-first and include:

- parameterized Repository Protocol cases against SQLite and PostgreSQL;
- empty database migration and unchanged re-run;
- advisory-lock serialization and migration checksum drift;
- foreign-key, unique, status check, append-only, terminal immutability, and identity immutability enforcement;
- exact idempotency-key/command-hash conflict behavior;
- optimistic CAS and concurrent claim behavior;
- retry, restart, recovery, snapshot, replay, and tamper rejection;
- SQLite-to-PostgreSQL fixture imports with count, primary-key, digest, and Reader equivalence;
- identity sequence repair after explicit-ID import;
- non-empty target and changed-source refusal;
- credential redaction and missing-configuration failure;
- CLI backend selection and incompatible-argument rejection;
- canonical lifecycle and controlled-operation PostgreSQL integration smoke tests.

GitHub Actions receives a pinned PostgreSQL service for integration tests. Local and CI tests must create isolated databases or schemas, never reuse the operator's authoritative local database, and clean only their exact test resources.

The final validation matrix includes:

```text
git diff --check
python scripts/check_docs_links.py
python -m pytest -q tests/scripts/test_check_docs_links.py
python -m pytest -q tests/platform
python -m pytest -q
python -m ruff check .
python -m mypy
python -m build
```

Additional PostgreSQL bootstrap, migration, repository, concurrency, import, and smoke commands must be reported as `PASS`, `FAIL`, `NOT_RUN`, or `BLOCKED` and bound to the exact tested HEAD.

## 13. Documentation and evidence

Implementation updates must reconcile:

- `docs/status/Current-State.md`;
- the Capability Matrix;
- the Gap Register;
- persistence architecture documentation;
- operator bootstrap, migration, backup, cutover, and recovery instructions;

Documentation must continue to state that local PostgreSQL parity is not production qualification, formal data authority, Shadow readiness, authenticated operator readiness, or trading authority.

## 14. Delivery phases

The implementation proceeds through dependency-coherent checkpoints:

1. PostgreSQL settings, secure bootstrap, migration runner, and CI service.
2. PostgreSQL schema and invariant enforcement.
3. domain authority repositories for versions 001 through 010.
4. Daily, Canonical Lifecycle, and Feature Materialization repositories.
5. Controlled Operation and Longitudinal Operational repositories.
6. composition roots and PostgreSQL-default CLI migration.
7. SQLite importer, migration evidence, backup, and cutover tooling.
8. local bootstrap, schema-only import, smoke cutover, full regression, and status reconciliation.

Each phase requires executable behavior, focused tests, regression evidence, documentation where facts changed, and a reviewable checkpoint commit. Ordinary implementation failures are forward-repaired within the phase.

## 15. Acceptance criteria

The design is implemented when all of the following are observed on the same final HEAD:

- the dedicated local role, database, and schema exist with the approved security attributes;
- no administrator or application secret is tracked by Git;
- all PostgreSQL migrations apply from an empty database and verify their checksums;
- all in-scope Repository Protocol behavior passes against PostgreSQL;
- ordinary runtime and CLI composition defaults to PostgreSQL and fails closed without configuration;
- SQLite remains available only through explicit compatibility selection;
- the importer proves the current schema-only `0 -> 0` migration or imports supplied SQLite sources with exact validation;
- canonical lifecycle and controlled operation complete PostgreSQL smoke scenarios;
- required local and CI validation is green;
- current-state documentation accurately states the new persistence boundary and remaining non-claims;
- `.idea/modules.xml` and all other unrelated user changes remain untouched.
